# learning_skills · 产品经理如何制作「可演示的 AI Skill」

> 这个仓库是**产品经理学习如何写 Skill** 的练习场。它不是一套生产系统，而是把「一个业务想法」落成「一条能让 AI 一步步跑给你看、能说服老板/客户的演示链路」的方法论 + 两个完整范例。

仓库里有两个范例项目，各演示一种 Skill 的形态：

| 项目 | 业务领域 | Skill 形态 | 演示效果 |
|---|---|---|---|
| [fresh-food-supplier](fresh-food-supplier/README.md) | 生鲜供应（接单→采购→配送） | **单 Skill + 多脚本**，确定性 Python 按层处理 | 口语下单 → 一条指令跑通 L1→L4，`data/` 里每层都有可见产物 |
| [LLM-token-provider](LLM-token-provider/README.md) | Token 工厂商业化（定价→计费→对账→评审） | **四 Skill 串联成体系**，双输出（严格 JSON + HTML 报告） | A→B→C→D 形成商业化闭环，每一步产出机器可读 + 老板可看的双份结果 |

---

## 一、这个仓库在教什么

1. **Skill 是什么**：一份给 AI 看的「操作手册」——告诉它这个业务怎么做、按什么流程、什么数据、什么规则。
2. **Skill 怎么写**：frontmatter（触发条件 + 职责边界）+ 正文（流程 / 规则 / 数据契约 / 注意事项）的结构化写法。
3. **如何根据业务需求做演示 demo**：把业务拆成"输入 → 确定性计算 → 可见产物"的链路，让 AI 能一步步执行、每一步都有可展示的证据。

## 二、Skill 的通用结构

每个 Skill 是一个目录，核心是 `SKILL.md`（AI 读它决定怎么做），必要时配 `scripts/`（确定性 Python）和 `data/`（数据/配置）。

### 1. SKILL.md 的 frontmatter（AI 判断"何时用它"）

```yaml
---
name: token-billing
description: >-
  <一句话说清：什么场景下触发？输入什么？输出什么？边界在哪？>
  <与其他 skill 的上下游关系>
---
```

`description` 是 skill 的「触发说明书」，AI 靠它决定什么时候调用这个 skill。

### 2. SKILL.md 正文（AI 决定"怎么做"）

好的 skill 正文包含以下模块（范例里都有，可对照学习）：

| 模块 | 回答的问题 | 范例位置 |
|---|---|---|
| 定位 / 边界 | 这个 skill 负责什么、**不**负责什么 | 每个 SKILL.md 开头 |
| 工作目录约定 | 所有路径怎么定位（相对路径，禁止写死本机绝对路径） | `## 工作目录` |
| 输入要求 | 用户需要提供什么、缺省用什么默认值 | `## 输入要求` |
| 工作流程 | 分 Step 的操作步骤，每步产出什么 | `## 工作流程` |
| 数据契约 | 与上下游 skill 的字段约定（对齐，不各造一套） | `## 上下游与数据契约` |
| 计算真实性 | 哪些必须跑脚本、禁止心算/凭记忆 | `## ⚠️ 计算真实性要求` |
| 输出格式 | 机器可读（严格 JSON）+ 演示层（HTML 报告） | `## 输出格式` |
| 注意事项 | 血泪教训、行业口径、必须遵守的铁律 | `## 注意事项` |

### 3. scripts/（把规则变成确定性代码）

**原则：流程交给 AI（编排、解析口语、弹窗确认），计算交给脚本（确定性、可审计、禁止心算）。**

- 脚本只接「已确认的结构化参数」，自己不懂自然语言 / 文件格式（文件由 AI 读取解析）。
- 计算类规则（费用、对账、毛利、定价）必须固化在脚本里，禁止 AI 心算——这也是"演示可信"的根基。
- 脚本输出写进 `data/`，让每一步都有**可见产物**，观众能亲眼看到数据逐层流转。

### 4. data/（演示的数据底座）

业务配置（客户、价格、映射表）与中间产物（每层的 CSV / JSON）。改 `data/` 里的配置就能演示不同业务走向。

## 三、如何根据业务需求制作演示 demo（方法论）

拿到一个业务想法，按下面四步落地成可演示的 Skill：

**Step 1 · 拆业务链路**

把业务画成一条链：`输入 → 中间处理（若干步）→ 输出`。生鲜例子是「接单→编码→风控→采购/分单」，Token 例子是「定价→计费→对账→评审」。每一步要有明确输入、明确产出。

**Step 2 · 定"哪步给 AI、哪步给脚本"**

- **给 AI（编排层）**：理解自然语言、解析口语/图片/表格、弹窗与用户确认、按流程调度脚本。
- **给脚本（确定性层）**：凡是"规则明确、算错即丢钱/失信"的计算，全部固化进 Python。
- 判断标准：**能不能算错？** 能错 → 给脚本；只是理解/判断 → 给 AI。

**Step 3 · 让每一步有"可见产物"**

演示的核心是"看得见"。每一步脚本跑完都要往 `data/` 写一个文件（CSV/JSON），AI 每跑完一步就展示"这一步产出了什么"。观众看到的不是"黑盒输出一句话"，而是**一条数据在各层之间流转的证据链**。

**Step 4 · 设计"叙事落点"**

想清楚这段演示**要说服谁**：
- 给老板看 → 双输出（机器可读 JSON + HTML 报告），结论一屏看懂；
- 给客户/业务看 → 中间产物逐步展示（"这里自动识别了别名""这里异常转人工了"）；
- 给自己验证 → 一个 `reset.py` 类脚本随时重置演示态，可反复排练。

## 四、两个范例怎么读

- **先读根目录**（本文件）→ 理解"skill 怎么写、demo 怎么做"的整体思路。
- **再读 [fresh-food-supplier/README.md](fresh-food-supplier/README.md)** → 看一个**单 skill** 如何把口语下单变成逐层可见的接单-采购-配送闭环。
- **然后读 [LLM-token-provider/README.md](LLM-token-provider/README.md)** → 看**四个 skill 如何串成体系**，如何做"机器可读 + 老板可看"的双输出。

## 五、目录结构

```
learning_skills/
├── README.md                  # 本文件：项目定位 + skill 写法 + demo 方法论
├── fresh-food-supplier/       # 范例一：生鲜供应（单 skill，确定性分层）
│   ├── README.md
│   └── mock-bill-submission/  # skill：接单→采购→配送
├── LLM-token-provider/        # 范例二：Token 工厂商业化（四 skill 体系）
│   ├── README.md
│   ├── token-cost-pricing/    # Skill A：成本核算与定价
│   ├── token-billing/         # Skill B：计量与计费
│   ├── token-reconciliation/  # Skill C：对账与账单
│   └── token-review/          # Skill D：商业化评审
└── test/                      # skill 生成的产物统一存放处（JSON + HTML）
```

> **写 Skill 的一条铁律**：所有路径用**相对路径**（相对于 skill 所在项目根目录），禁止写死本机绝对路径——否则 skill 换个机器/项目就跑不通，demo 也就"只能在自己电脑上演"了。
